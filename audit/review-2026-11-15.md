## 2. 本轮新发现

### N1【High】`ext4 build --block-size 1024` 无法构建 ≥ 8 MiB 的单文件（实测硬失败，报错误导）

位置：`src/ext4/write.rs:354`（`let chunk = left.min(8192);`）、`src/ext4/write.rs:643-668`（`alloc_contig`）

**现象（实测，`tmp/rev_ext4_2.sh`）**

```
--- 7 MiB file, --size 512M, bs 1024 ---   wrote ok1k.img   e2fsck exit=0
--- 7 MiB + 8 MiB files, --size 512M, bs 1024 ---  error: no space left for 8192 blocks (image too small, pass --size)
--- same but --size 1G ---                          error: no space left for 8192 blocks (image too small, pass --size)
```

**根因**：分配单元固定为 **8192 个块**并要求**整段连续**。1K 块时 `bpg = 8*bs = 8192` 块，
而每组头部至少占 `SB+GDT+2 位图+inode table`（`ipg=2048` → itable 512 块）≈ 515 块，
组内最长连续空闲 run 恒 < 8192 → **永远分配失败，与 `--size` 无关**。
`--size 1G` 仍然报同样的错，说明错误信息（"image too small, pass --size"）把用户引向错误方向。

顺带：4K 块下同一缺陷的阈值是"单文件 ≈ 126 MiB"。因 4K 的 `bpg=32768`、每组头部 516 块，
8192 块 run 仍能放下，所以 4K 暂不触发；**1K 必触发，4K 在 `--block-size` 未来放宽时会触发**。

**影响**：`--block-size 1024` 是 CLI 暴露的合法参数（`main.rs:276`），带大文件（APK/oat/vendor blob）
的树在 1K 块下根本构建不出来；报错指向错误原因，用户会反复加大 `--size`。

**修复建议**（与 e2fsprogs 一致：**按 run 分配，一个 run 一个 extent**）

```rust
// 把"要求 n 块连续"改成"尽量分配，返回实际长度"
fn alloc_run(max: u64, used: &mut [bool], cursor: &mut u64) -> Result<(u64 /*start*/, u64 /*len*/)> {
    // 从 cursor 起找第一个空闲块，再向后延伸到下一个已用块或 max
}
// 循环直到 left == 0，每轮 push 一个 ExtentLeaf{logical, len, start}
```

最小改动版：`for n in [8192, 4096, 2048, 1024, 256, 64, 16, 1]`，第一个成功的就用。
另外把错误信息改成 `no contiguous run of N blocks left (image has M free blocks in K runs)`。

### N2【High】构建/解包全量进内存：真机尺寸镜像必 OOM

位置与实测峰值：

| 路径 | 代码 | 峰值内存 |
|---|---|---|
| `ext4 build` | `write.rs:345` `fs::read(&host)` + `write.rs:300` `extra_blocks: Vec<(u64, Vec<u8>)>` 持有**整个镜像内容** | 160 MiB 文件 → **334 MiB RSS**（`/usr/bin/time -f %M` 实测） |
| `ext4 extract` | `read.rs:173-222` `read_data` 整文件 `Vec`；`read.rs:351-353` 再 `fs::write` | ≈ 2× 单文件大小 |
| `payload build` | `payload.rs:757` `fs::read` + `payload.rs:753,792` `blobs: Vec<Vec<u8>>` | ≈ 2× 分区大小 |
| `payload extract` | `payload.rs:476-489` `read_extents` 整段 `Vec` + 解压后整段 | ≈ 2–3× 单 op |
| `dat patch` | `dat.rs:211-226` `read_ranges` 整段 | ≈ 2× rangeset |
| `super build` | `superimg.rs:766-767` `copy_range` 1 MiB 缓冲 | ✅ 已是流式 |
| `sparse to_raw` | `sparse.rs:143` 1 MiB 缓冲 | ✅ 已是流式 |

**影响**：目标机（Windows，8 GB 物理内存、常年仅剩 0.7–1 GB）上构建 2–3 GB 的
`system.img`/`payload.bin` 必然 OOM；这不是"慢"，是**做不出来**。README §4 的主流程
（`--size 3G`）在当前架构下不可执行。

**修复建议**

1. `ext4 build`：把 `extra_blocks` 从 `Vec<(u64, Vec<u8>)>` 改成"边分配边写盘"——
   `alloc_contig` 返回块号后立即 `write_at(&mut f, blk*bs, chunk)`；文件读取改成
   `File::open` + 固定 1–4 MiB 缓冲 + `read_exact`。峰值内存降到 O(4 MiB + inode 表)。
   代价：`create_sized(out, size)` 必须提前建好（目前也是先建后写，改动很小）。
2. `ext4 extract`：`read_data` 拆成 `walk_extents + stream_to(writer)`，`io::copy` 语义。
3. `payload build`：`blobs` 改成"先写 blob 区、边算哈希边记 offset"，manifest 最后回填空位
   （v2 header 的 manifest 长度字段需要预留或分两趟：第一趟只算 ops，第二趟真写）。
4. `payload extract` / `dat patch`：按 1 MiB 切块流式处理（blockimg 本身就是 1 MiB 流式）。

### N3【Medium-High】`super make` 的 `meta_end` 少算 4096 字节保留区 → `--alignment < 1 MiB` 时分区数据压进 metadata 区

位置：`src/superimg.rs:648-650`

```rust
let meta_end = GEOMETRY_SIZE * 2 + opt.metadata_max_size as u64 * opt.metadata_slots as u64 * 2;
//            = 8192 + max*slots*2           ← 漏了 LP_PARTITION_RESERVED_BYTES = 4096
```

liblp 真实布局：`[reserved 4096][geometry 4096][backup geometry 4096][primary slot0..N][backup slot0..N]`，
即 metadata 区结束于 `4096 + 8192 + max*slots*2 = 12288 + max*slots*2`。

默认参数（`max=65536, slots=2, alignment=1048576`）下 `meta_end=270336`、真实结束 `274432`，
因 1 MiB 对齐 > 274432 被掩盖。但 `super make --alignment 4096` 时
`first_logical_sector = 270336/512 = 528`，而 backup slot 1 覆盖 `208896..274432`
→ 首个分区的前 4 KiB 落在 metadata 区内。设备侧 `lpflash`/metadata 回写会覆盖该分区头部，
`lpmake` 自身也会拒绝这种重叠布局。

**修复**：`let meta_end = 4096 + GEOMETRY_SIZE * 2 + max*slots*2;`，并把 `first_logical`
再对齐到 `logical_block_size`（当前只按 `device_alignment` 对齐）。

### N4【Medium-High】`super unpack` 的后缀剥离在真实 A/B super 上永不生效（与 README §3.2 描述不符）

位置：`src/superimg.rs:441-455`

```rust
let collides = meta.partitions.iter().any(|q| q.name != p.name
    && (q.name == format!("{}_a", base) || q.name == format!("{}_b", base)));
if !collides { name = base; }
```

`collides` 统计的是**metadata 里的全部**分区，包括被 `--slot` 过滤掉的 `_b`。真实 super.img
同时列出 `system_a` 与 `system_b`，因此 `system_a` 判定为"冲突"→ 保留 `system_a.img`。
连带影响：`keep_suffix` 在 A/B 情况下变成 no-op；README §3.2 的
"`--slot 0` 只导出无后缀与 `*_a`" 与实际输出不符。

（e2e 用例 `tests/e2e.rs:180` 只造了单个 `system_a`，恰好走到剥离分支，所以测试通过、问题被掩盖。）

**修复**：`collides` 只在"将被导出"的分区集合内计算（先按 slot/partitions 过滤，再判重）。

### N5【Medium】`super make` 不校验分区镜像是否为 raw：sparse 镜像会被原样塞进 super

位置：`src/superimg.rs:761-768`（无任何 `sparse::is_sparse` 检查）

`super make --partition system_a=system.img` 若 `system.img` 是 sparse 镜像（README §4 第 5 步
`sparse from-raw` 之后就产出这种文件），会被 1:1 拷进 super，设备侧 `dm-linear` 映射后
`mount` 得到"文件系统魔数错误"。没有任何警告。

同类不一致：`super`/`payload` 入口有 `open_maybe_sparse`（`superimg.rs:125-134`），
`ext4` 没有（`main.rs:613` 直接 `Ext4::open`）→ 对 sparse 输入只报 `bad ext4 magic 0x...`。

**修复**：`build` 拷入前 `if sparse::file_is_sparse(&p.image)? { bail!("...run `sparse to-raw` first") }`；
`Ext4::open` 里同样探测并自动展开（或给出明确提示）。

### N6【Medium】payload：不支持 `BSDF2`、无 `payload_properties.txt`、末块未补齐

1. **BSDF2（brotli/raw 变体 bsdiff）**：`payload.rs:645` 只认 `BSDIFF40`。Android 10+ 的
   delta OTA 里 `SOURCE_BSDIFF` 常用 `BSDF2`（第三个流按压缩器 id 选择 bz2/brotli/raw），
   参考实现 `vendor/payload-dumper-go` 同时支持两者。当前对这类包会
   `error: bad bsdiff patch`，而 README §3.4 声称支持 `SOURCE_BSDIFF`。
   （未用真实样本验证：手上没有 BSDF2 的 payload。）
2. **`payload make` 不产出 `payload_properties.txt`**（`FILE_HASH` / `FILE_SIZE` /
   `METADATA_HASH` / `METADATA_SIZE`）。`update_engine_client` / 某些刷机脚本需要它才能校验；
   `adb sideload` 不需要。属于已知缺口但值得在 README §7 明写。
3. **末块**：`build` 用 `end = min((b+nb)*BLOCK, data.len())`，非块对齐镜像（如 100 000 字节的
   boot.img）最后一个 op 为 `dst_extents=[{nb:1}]` 但 `dst_length=1696`。自家 extract 能往返，
   但设备侧 `DeltaPerformer` 对 `dst_length != extents_bytes` 的容忍度取决于版本（`delta_generator`
   会把尾块补零到整块）。建议补零并对齐 `new_info.size`。

### N7【Medium】`.dat`：`split` 不做 gap 检测、`patch` 数据不足时静默保留旧数据、输出重名失败

位置：`src/dat.rs:326-352`、`src/dat.rs:228-249`、`src/dat.rs:321`

1. `split` 直接 `fs::copy` 整个 raw 镜像进 `new.dat`，只发一条 `new 0..blocks`，**不做空闲块裁剪**
   （真 `img2sdat` 会扫 ext4/f2fs 位图输出 `erase`，产物小 30–50%）。功能正确但语义上与
   `img2sdat` 不等价，README 未说明。
2. `write_ranges`：`let n = buf.len().min(data.len() - off); if n == 0 { return Ok(()) }`
   —— 数据比 dst rangeset 短时**直接返回**，剩余块保留 base 旧数据（blockimg 语义是补 0 或报错）。
   静默产出错镜像，建议 `bail!` 或补零。
3. `patch` 用 `std::fs::rename(&tmp, out)`：Windows 上目标已存在时 `rename` 直接失败
   （`ERROR_ALREADY_EXISTS`），第二次打同一个输出名会报错；建议先 `remove_file` 或 `fs::copy`。
4. `patch_stream_offset`（`dat.rs:420-426`）读一行然后恒返回 0，是死代码。
5. `stash`/`free` 被忽略，注释称"源始终从只读 base 读"。对 `move` 在 blockimg 里是
   **从目标（已写）读**，`new` 之后的 `move` 会读错源。旧 `.dat` 差分包可能踩到；
   README §7 已声明该假设，建议改为对 `move` 直接读 `dst` 文件。

### N8【Medium】ext4 构建器为每个 inode 分配一个 4 KiB 外部 xattr 块（未实现 ibody）

位置：`src/ext4/write.rs:461-488`

只有 `security.selinux`（26 B）也单独占一个 4 KiB 块、`h_refcount=1`，不做共享。2 万文件的
`system.img` 白付 ≈ 80 MiB，且与 `e2fsdroid` 产物形态不同（它把 label 写进 inode 内联区）。
读取侧 `read.rs:255-303` 已完整支持 ibody，**写入侧补齐即可**：inode_size=256、
`i_extra_isize=32` 时内联区 96 B，`16 + 15 + 26(+pad)` ≈ 60 B，放得下。
（`e2fsck` 接受当前写法，所以这是效率/一致性缺陷，不是正确性问题。）

### N10【Low】boot v3/v4 解析把别人的字段当地址写进 `boot.json`

位置：`src/boot.rs:169-173`（对所有版本都执行）

v3/v4 头部没有 `kernel_addr/ramdisk_addr/second_addr/tags_addr`（offset 12 是 `ramdisk_size`、
20 是 `header_size`、24..40 是 reserved）。因此 v3/v4 的 `boot.json` 里
`kernel_addr = ramdisk_size`、`ramdisk_addr = header_size`、`tags_addr = 0`。
`build()` 对 v3/v4 不写这些字段，所以重打包无影响；但 `boot.json` 内容误导人。
建议 v≥3 时置 0 或标 `null`。

### N11【Low】`Cargo.lock` 与 `Cargo.toml` 不同步

`Cargo.toml:32` 依赖 `xz2`，但 `Cargo.lock` 里没有 `xz2`/`lzma-sys` 记录
（`cargo build` 提示 `Locking 2 packages… Adding lzma-sys v0.1.20 / xz2 v0.1.7`）。
`cargo build --locked` / `--frozen` 会直接失败，可复现构建不成立。**本次构建已自动补齐**
（见副作用声明），建议提交这一版 lock。

### N12【Low】死代码（`pub` 所以没有 warning）

### N13【Low】`safe_component` 与解包落盘的边界情况

- 未处理 Windows 的"尾部点/空格"归一化（`foo.` 与 `foo` 落成同一文件）与大小写不敏感冲突
  （ext4 里 `Foo`/`foo` 会静默互相覆盖，`super unpack` 有 `seen` 保护，`ext4 extract` 没有）。
- `extract_tree` 不校验**输出目录里已存在**的 junction/symlink：若 `out/system` 之前被建成
  指向别处的链接，后续 `create_dir_all(out/system/bin)` 会写到树外。属于"解包器不得不防"的一类，
  建议 `fs::symlink_metadata` 检查每个中间目录不是链接。

### N14【Low】`MetaDb::from_dir` 不记录 `ino` → 从 Windows 目录树构建永远丢失硬链接

`perm.rs:429-441` 的 `ino: None` 是常量。硬链接只在"从 ext4 镜像解包"这条路上被保留
（`read.rs:387`）。从 Windows 树 `perm export` → `ext4 build` 的路径上，硬链接会变成多份副本。
建议 `from_dir` 用 `(dev, ino)`（Windows 可用 `file_index`）填充 `ino`。

### N15【Low】`payload extract --verify` 的 CLI 形态

`main.rs:178`：`default_value_t = true` + `ArgAction::Set` → `--verify` 必须带值
（`--verify true`），单独写 `--verify` 会报错。建议 `ArgAction::SetTrue` + `--no-verify`，
或用 `num_args(0..=1) + default_missing_value("true")`。

### N16【Low】性能与小溢出

- `ext4/read.rs:465` `tree_rec` 每条目都 `out.lines().count()`（O(n²)），20 万条目时会明显卡。
- `util.rs:9-14` `align_up` 的 `v + a - 1`、`util.rs:95-109` `parse_size` 的 `v * mult`
  在大输入下 debug 会 panic / release 会回绕。加 `checked_*` 或 `?`。
- `ext4/write.rs:549`、`disk.rs:554` `rec_len as u16`：`--block-size 65536` 时 `bs - off = 65536`
  溢出为 0。当前 CLI 允许 65536（`power_of_two >= 1024`），建议上限钳到 32768 或改用
  `u16::MAX` 特判。

### N17【Low】README §8 的验证结论已过期

§8/§8.1 的 `cargo test 18+2 / e2fsck clean` 是 **2026-11-10** 的结果，而 `write.rs`/`read.rs`/
`disk.rs` 在 **11-15 15:57–16:11** 被大改（C1/C2/M3/M4 修复 + 新修复项）。文档里的验证
不覆盖当前代码。本报告的实测（§0、§1 表格）可以替换它；建议 README §8 换成可复跑的脚本
（`scripts/verify_ext4.sh` 已有雏形，但没有多组/1K/大文件用例）。
